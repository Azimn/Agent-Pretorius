EXECUTIVE SUMMARY
This specification defines a character-agnostic persona framework that completely
separates:
1. Framework Code (the execution engine - reusable across ALL characters)
2. Persona Data (character definitions in .snp files - portable, versionable)
3. Runtime State (per-conversation memory - ephemeral, user-specific)
Key Innovation: The framework is a “console” that runs persona “cartridges.” One
codebase can host unlimited characters without modification.

Why TOML over JSON?
TOML advantages:
Human-readable (like YAML)
Less ambiguous parsing
Supports comments
Used by Rust/Python ecosystems
Example:
# This is readable
[state_machine.variables]
trust = { type = "int", min = 0, max = 100, default = 30 }
# vs JSON
{
 "state_machine": {
 "variables": {
 "trust": {"type": "int", "min": 0, "max": 100, "default": 30}
 }
 }
}
Why Three Layers?
Separation of concerns:
Framework = Physics engine (defines rules of reality)Persona = Game cartridge (defines specific experience)
State = Save file (tracks progress)
Benefits:
Swap personas without changing framework
Version personas independently<PARSED TEXT FOR PAGE: 27 / 29>Distribute personas as files
Why State Machine in Persona File?
Enables:
Character-specific logic without framework changes
Tier 1 can execute without LLM
Portable across different framework implementations
Alternative (rejected): Hardcode all logic in Python
Would require code changes for each character
Not portable
Can’t hot-reload
Why Lamport Clocks?
Solves: Offline sync conflicts
Problem:
Device A (offline): User says "I love magic" → trust +10
Device B (online): User says "I hate magic" → trust -10
Devices sync. What's the final trust value?
Solution: Lamport timestamps create causal ordering
Event 1: (device_A, clock=5) trust +10
Event 2: (device_B, clock=7) trust -10
Merge: Sort by clock → E1 then E2 → final trust = 0 + 10 - 10 = 0
